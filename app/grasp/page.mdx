# GRASP

GRASP (General Responsibility Assignment Software Patterns) helps you decide which class gets which task.
A task in a design is called a responsibility.
This page covers three of them: Controller, Creator and Information Expert.

## Which principle do I need?

```plantuml
start
if (Who receives a system\noperation from the UI?) then (yes)
  :Controller: the class for the whole system,
  such as Library or Game;
  stop
endif
if (Who makes new\nobjects of class A?) then (yes)
  if (Does B contain or\nrecord A objects?) then (yes)
    :Creator: B creates A;
  else (no)
    :Creator: B closely uses A,
    or B has the data to make A;
  endif
  stop
endif
:Information Expert:
the class that has the data
(who does this calculation or task?);
stop
```

## Controller

A system operation is something the user asks the system to do, such as "lend this book".
The Controller is the first object behind the user interface (UI) that receives a system operation.
It does not do all the work itself: it finds the right objects and delegates the steps to them.

Choose a class that represents the whole system, such as `Library` or `Game` (a facade controller).
Another option is a class for one use case, such as `LendHandler`.
The UI stays thin, so you can reuse and test the logic without it.

```plantuml
participant ":LoanScreen" as UI
participant ":Library" as B
participant ":Borrower" as L

UI -> B : book = findBook(isbn)
UI -> U ** : create(borrower, book)
UI -> L : add(u)
UI -> BK : setLent(true)
```

The UI knows four classes and does every step.

</Side>
<Side kind="good" title="The Controller coordinates">

```plantuml

B -> B : book = findBook(isbn)
B -> L : borrow(book)

```

The UI makes one call.

</Side>
</Compare>

## Creator

Class B creates objects of class A when:

- B contains or aggregates A objects. This is the strongest reason.
- B records A objects.
- B closely uses A objects.
- B has the data that A needs when it is created.

The filled diamond is the hint: `Order` contains its `OrderLine` objects, so it creates them.
`Product` is used by a line, but does not contain lines.

```plantuml
left to right direction
class Order {
  +add(product : Product, quantity : int) : void
}
class OrderLine
class Product
hide empty members
Order "1" *-- "1..*" OrderLine : lines
OrderLine "*" --> "1" Product : refers to
```

```plantuml
actor Customer as K
participant ":Order" as B
participant ":OrderLine" as R
K -> B : add(bike, 1)
activate B
B -> R ** : create(bike, 1)
B -> B : lines.add(line)
deactivate B
```

## Information Expert

Give a task to the class that has the information to do it.
That gives high cohesion and low coupling.

The total open fines of one borrower:

- `Loan` knows its return date and its book, so it calculates the fine of one loan.
- `Borrower` knows all its loans, so it calculates the total.
- `Book` only knows the rate per day, not the loans of a borrower.
- `Library` could find the loans, but it would need data from other classes.

```plantuml
participant ":Library" as B
participant ":Borrower" as L
participant ":Loan" as U
participant ":Book" as BK
B -> L : openFines()
activate L
loop for each Loan
  L -> U : fine()
  activate U
  U -> BK : getFinePerDay()
  BK --> U : finePerDay
  U --> L : fine of one loan
  deactivate U
end
L --> B : total
deactivate L
```

## A game domain

```plantuml
hide circle
hide empty members
left to right direction
Game "1" -- "1" GameBoard : has >
GameBoard "1" *-- "*" Square : consists of >
Character "*" -- "1" Square : stands on >
```

- `Game` represents the whole game, so it is the Controller.
- `GameBoard` contains the Squares, so it is the Creator of Square.
- `GameBoard` is also the only class with the list of Squares, so it is the Information Expert for finding a free Square.

Each principle leaves a clue in the code.
